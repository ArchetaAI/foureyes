# D0.1: One-sentence promise and three non-goals
Status: Decided | Date: 2026-10-13

## Context
Every later scope decision is tested against the promise. It is also the first line of the README and the anchor for what we claim in public (the public-claims decision, D4.1). The working draft was: "give it a spec, get back code that passes gates your agent couldn't game, plus a report of what's still risky."

That draft holds in the benchmark, where hidden tests sit outside the agent's workspace. It does not hold in a user's own repo, because nothing in the planned core loop (gates, triage, a capped fix loop, stall detection, the evidence report) produces tests the agent can't see. Mutation score catches weak tests. It does not catch tests that encode the wrong behaviour. The promise has to be true on day one, not after a component we haven't built or measured.

## Options considered
| Option | Promise | Why not chosen |
|---|---|---|
| A. Draft as-is | Give it a spec, get back code that passes gates your agent couldn't game, plus a report of what's still risky. | Overclaims for real use unless an independent test-writing stage exists; that stage is unbuilt and unmeasured |
| **B. Bring-your-own hidden tests** | Give it a spec and acceptance tests the agent never sees; get back code that passes them, plus a report of what's still risky. | **Chosen** |
| C. Lift-led | Makes Claude Code, Codex and OpenCode measurably better on hidden tests, and shows its work. | Rests on benchmark results we don't have yet |
| D. Evidence-only | Every agent run ends with an evidence report: what passed, what was waived, what's still risky. | Drops the anti-gaming property that makes the project different |

## Decision
**Promise:** Give it a spec and acceptance tests the agent never sees; get back code that passes them, plus a report of what's still risky.

**Non-goals:**
1. Not a new coding agent. foureyes runs on top of existing agents (Claude Code, Codex, OpenCode) through adapters.
2. Not a multi-agent swarm. One agent builds at each stage; a reviewer from a different vendor files findings and never edits.
3. Not a prompt pack. The value is in the gates, triage, loop and evidence, not in prompt wording.

**Where the un-gameable tests come from in v1:** the user supplies the acceptance tests, and the workflow keeps them out of the agent's context. In the benchmark, the hidden tests play this role. foureyes does not generate its own held-out tests in v1.

## Consequences: what this commits us to and what it rules out
- The workflow must accept user-supplied acceptance tests, keep them outside the agent's workspace, and run them only through the harness. This shapes where hidden tests live (D1.4), the stage model and run state (D2.1), and the gate interface (D2.2).
- The quickstart and example repo must ship with acceptance tests, so a newcomer sees the whole promise on their first run.
- Public claims (D4.1) cannot say foureyes writes or guarantees tests by itself, or that gates "can't be gamed" without user-supplied hidden tests.
- Users with no tests still get gates, mutation score, review and a report, but not the core promise. The README must say so plainly.
- Rules out: a test-generation stage in v1; any feature that lets the agent read acceptance tests; the lift-led promise.

## Revisit if
- A stage from a different vendor that writes acceptance tests from the spec, hidden from the building agent, is proposed as its own decision, and a benchmark ablation shows it adds lift without user-supplied tests. Then reconsider option A.
- Benchmark results show a large, stable lift across agents, and leading with the number would serve users better than leading with the guarantee.
- Early users consistently lack acceptance tests and drop off at that step.
