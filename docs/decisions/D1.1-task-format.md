# D1.1: Task format: folder layout, metadata, visible vs hidden tests
Status: Decided | Date: 2026-10-14

## Context
The benchmark needs one format for every task: 15 tasks, 7 repair and 8 greenfield, all in TypeScript per the first task language (D0.4). Hidden tests, reference solutions and held-out tasks live in the private repo, with only SHA-256 hashes public (D1.4). The format has to keep what the agent sees cleanly separate from what grades it, let a stranger inspect any public task, and make "solved" mean something precise. Isolation (D1.3), the results schema (D1.5) and mutation testing (D1.6) are still open, so this format reserves room for them without deciding them.

## Options considered
| Option | What it is | Why not chosen |
|---|---|---|
| **A. Own minimal folder format** | Each task is a plain folder: metadata, prompt and starting repo in public; hidden tests and the reference solution in private | **Chosen**, with B's grading semantics |
| B. SWE-bench-style patch records | One record per task: base snapshot, hidden test patch, gold patch, fail-to-pass and pass-to-pass lists | The starting state is unreadable as patches, and a greenfield gold patch is the whole implementation. Its grading semantics are adopted |
| C. Terminal-Bench-compatible folders | Match an existing public harness's task layout, moving tests to the private repo | That format keeps tests in the task folder and assumes a container image per task. It conflicts with D1.4, pre-empts D1.3, and the split breaks compatibility anyway |

## Decision
**Option A, with fail-to-pass and pass-to-pass grading.**

### Layout
Public repo (`ArchetaAI/foureyes`), for the 10 tuning tasks:
```
benchmark/
  hidden-manifest.json     SHA-256 of every hidden file (see Manifest)
  tasks/<id>/
    task.yaml              public metadata
    prompt.md              exactly what the agent is told
    repo/                  the starting repo, including visible tests
```
Private repo (`ArchetaAI/foureyes-bench-private`):
```
tasks/<id>/
  hidden.yaml              hidden metadata: test lists and the hidden test command
  hidden/                  hidden test files, mirroring repo/ paths
  solution.patch           reference solution
```
- **Held-out tasks:** each one's complete folder, including `task.yaml`, `prompt.md` and `repo/`, lives only in the private repo under `tasks/<id>/`. Held-out specs are private too.
- **IDs:** tuning tasks are `repair-NN` or `greenfield-NN`. Held-out tasks use opaque IDs (`h01`–`h05`), so a manifest entry reveals nothing about them.

### What the agent receives
Only `prompt.md` and a fresh copy of `repo/`. It never receives `task.yaml`, anything from the private repo, or the manifest.

### Public metadata: `task.yaml`
Validated against a versioned JSON Schema, starting at `schema_version: 1`:
- `id`: must match the folder name.
- `kind`: `repair` or `greenfield`.
- `split`: `tuning` or `held_out`.
- `dev_subset`: true for exactly 5 tuning tasks.
- `title`: one line.
- `toolchain`: the Node major version and package manager. Version 1 accepts `npm` only.
- `commands`: `install` and `test`. `test` runs the visible tests.
- `protected`: whole files, by path relative to `repo/`. The scorer restores each one from the starting repo before running hidden tests.
- `limits` (reserved, optional until the isolation decision, D1.3).
- `mutation` (reserved, optional until the mutation-testing decision, D1.6).

Nothing in `task.yaml` names or describes a hidden test.

### Hidden metadata: `hidden.yaml` (private)
- `fail_to_pass`: hidden tests that must fail on the starting repo and pass on a correct solution. Must not be empty.
- `pass_to_pass`: hidden tests that must pass both before and after. May be empty, for example for greenfield.
- `hidden_test`: the command that runs the hidden tests. It uses a scorer-owned test config shipped in `hidden/`, never a config the agent could have edited.

Each test is identified by its file path and its full test name, as the task's test runner reports them in machine-readable output.

### Grading
1. The scorer takes the agent's final `repo/` and restores every `protected` file.
2. It copies `hidden/` over the repo at the mirrored paths and runs `hidden_test`.
3. **A task is solved** only if every `fail_to_pass` test and every `pass_to_pass` test passes.

Which metrics get reported, including per-test pass rates, belongs to the results schema (D1.5).

### Reference solution: `solution.patch`
A unified diff against `repo/`, which must apply with `git apply` without fuzz. No binary changes.

### Validation
A task is valid only if all of these hold:
- **Metadata:** `task.yaml` and `hidden.yaml` pass their schemas.
- **Starting repo:** visible tests fail, every `fail_to_pass` test fails, and every `pass_to_pass` test passes.
- **With `solution.patch` applied:** all visible and hidden tests pass.
- **Determinism:** every hidden-test check gives the same result 3 times in a row. Any flake makes the task invalid.

### Manifest: `benchmark/hidden-manifest.json`
- **Contents:** `schema_version` and a list of `{ path, sha256 }` entries, sorted by path.
- **Coverage:** every file under `tasks/` in the private repo, plus held-out specs.
- **Paths:** relative to the private repo root.
- **Hashes:** computed over the bytes as committed, which are LF-only per `.gitattributes`.
- **Generation:** by script, never by hand.

### Toolchain and repo hygiene
- Each `repo/` commits its own `package.json` and lockfile, never `node_modules`. It has no nested `.git`.
- The root toolchain excludes `benchmark/tasks/**` entirely: the root `tsconfig.json`, ESLint, Vitest and Prettier. Visible tests fail by design, and seeded bugs and stub scaffolds must not be type-checked or linted as harness code.

## Consequences: what this commits us to and what it rules out
- **Root config changes.** The root `tsconfig.json` currently includes all of `benchmark`, and there is no Vitest config, so the default test glob would run every task's failing visible tests. The task-format work must narrow both and add matching ESLint and Prettier ignores.
- **Two schemas.** `task.yaml` and `hidden.yaml` each get a JSON Schema, and the validator checks both. When the private repo isn't available, as in public CI, it checks the public side and the manifest only.
- **No byte-identical files across the split.** Hidden files must not match any public file byte for byte, or the leak check reports a false leak.
- **Specs.** Spec authors must write tests the runner can identify by file and full name. Fail-to-pass must be non-empty, so every task needs at least one hidden test that a correct solution turns green.
- **Protected files aren't enough on their own.** A file not listed is fair game for the agent, and red-teaming may find tampering they can't cover, such as swapping a test dependency. The hidden test command running on a scorer-owned config narrows that, but the red-team results decide whether it is enough.
- **The agent's context is fixed.** It is `prompt.md` and `repo/`. The workflow's own staged context (D2.1) is added on top in workflow runs, not in plain-agent baselines.
- **Rules out:**
  - hidden test names or descriptions in any public file
  - per-task container images as part of the format (that's D1.3's call)
  - nested git repos inside tasks
  - package managers other than npm in schema version 1
  - giving the agent `task.yaml`

## Revisit if
- A task spec can't be expressed in this format.
- Red-teaming finds a cheat that protected files and a scorer-owned config can't close.
- Running foureyes tasks in an outside harness becomes a goal.
- A second task language, C# being the lead candidate, needs a non-npm toolchain.
- The isolation or mutation decisions (D1.3, D1.6) need fields the reserved slots can't hold.
